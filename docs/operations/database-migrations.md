# Database Migrations

This project uses Alembic for database schema migrations.

## Design Principle

Application startup should not automatically create or mutate database schema.

Schema changes must be explicit, reviewed, versioned, and applied through migrations.

## Local Database

Start local infrastructure:

    docker compose up --build

The local PostgreSQL database is configured through:

    DATABASE_URL=postgresql+psycopg://clinic:clinic@localhost:5432/clinic_receptionist

The actual value should come from `.env`.

## Alembic Configuration

Alembic is configured in:

    alembic.ini
    migrations/env.py

The migration environment imports:

    app.db.base.Base

This allows future SQLAlchemy models to be registered through the shared metadata.

## Creating a Migration

After adding or changing SQLAlchemy models, generate a migration:

    python -m alembic revision --autogenerate -m "create patients table"

Always review generated migrations before committing.

Autogenerated migrations are a starting point, not something to trust blindly.

## Applying Migrations

Apply all pending migrations:

    python -m alembic upgrade head

## Checking Current Revision

Check the current database revision:

    python -m alembic current

## Downgrading

Downgrade one migration:

    python -m alembic downgrade -1

Use downgrade carefully.

Production rollbacks should be planned and reviewed.

## Current Status

The project currently has Alembic configured, but no domain tables have been added yet.

The first real schema migration will be added when scheduling domain models are introduced.

## Operational Notes

- Do not run migrations automatically during application startup.
- Do not commit `.env`.
- Do not expose database credentials in logs or health responses.
- Review migration diffs before committing.
- Keep migrations small and tied to meaningful domain changes.
